Continuous Memory Model and Retrieval

Research track

Part 2 of the summer internship project Streaming Video LLM with Infinite Memory: how to store, organize, and retrieve from memory over a continuous video stream without keeping all past frames in the LLM context window.

Problem formulation

Show full description

Context. The parent project splits into (1) efficient stream processing and (2) efficient memory storage and retrieval. This track owns (2). Prior work proposes memory and streaming architecture adaptations, but none can hold effectively infinite video context while supporting rich natural-language queries at arbitrary future times.

Problem statement. Given a continuous video stream V = {f₁, f₂, …} arriving in real time, design a memory module M that:

  1. Ingests incrementally — writes new observations as frames or clips arrive, without requiring the full video upfront.
  2. Stores selectively — keeps salient information under bounded per-frame compute and storage cost.
  3. Retrieves on demand — answers natural-language queries Q by finding relevant temporal evidence, not by re-encoding the entire history into context.
  4. Scales in horizon — supports hours-to-days of egocentric or streaming video with retrieval cost that does not grow linearly with naive full-context attention.
  5. Grounds answers in evidence — returns intervals, events, or summaries traceable to stored frames, clips, or structured memory entries.
Example query

“What did I do between taking my phone out and putting it back in my pocket?”

Illustrative answer: You opened Instagram and scrolled through memes, then played Candy Crush and took some selfies.

Why this is hard. The query is not a single nearest-neighbor lookup. It requires multi-hop temporal reasoning:

  1. Find the anchor event: phone taken out.
  2. Find the closing anchor: phone put back in pocket.
  3. Traverse and summarize the segment between those anchors in a streaming-compatible way.

Standard vision–language embeddings (e.g. CLIP-style) alone are insufficient. The system likely needs an agentic loop: query → plan → search memory → inspect evidence → refine → answer. Storing entire days of video and retrieving efficiently at query time remains an open systems + modeling problem.

Starting direction. A concrete first baseline to explore:

  1. Extract frame or clip embeddings from the incoming stream.
  2. Store them in an external index (e.g. FAISS) with temporal metadata.
  3. Let an LLM agent navigate the index at query time — search, browse summaries, and inspect frames (DVD-style tool use is a relevant pattern).

Evaluation framing. Adapt existing long-horizon video benchmarks (e.g. Ego4D) and streaming interaction benchmarks (e.g. RIVER retrospective-memory tasks). Success means answering interval and event queries over long streams with evidence that can be inspected, not only generating plausible text.

  • Core task: build a memory module for video streams that never really end.
  • Main challenge: answer interval and event queries through evidence, not one-shot nearest-neighbor retrieval.
  • First baseline: combine clip embeddings, temporal metadata, vector search, and an LLM agent that inspects evidence.

Key notes

Show full description

The central research note is that “infinite memory” should not be framed as simply expanding the context window. It is a memory-management problem: what to write, how to compress or consolidate it, how to retrieve it later, and how to make the answer auditable through temporal evidence.

Near-term milestone. Start with an explicit, evidence-grounded memory baseline before exploring latent or generative memory:

  1. Stream observations into frame, clip, or event embeddings.
  2. Attach temporal metadata and lightweight summaries to each memory entry.
  3. Store entries in a vector index plus a timeline-aware metadata store.
  4. Use an LLM agent to search, inspect, and refine retrieval until it can answer with cited intervals or events.

Research emphasis. The important contribution is not only retrieval accuracy, but memory policy: deciding which observations become durable memories, when memories should be merged, and how retrieval can recover multi-hop temporal structure across long streams.

The intended direction is to leverage agents with tool-calling, policy improvement, and training so the system can decide when to interact, what to retrieve, and how to preserve memory.

Related-work baselines: RIVER, ReMEmbR, StreamBridge

Show full description

RIVER. RIVER is a real-time Video LLM interaction benchmark from OpenGVLab. Instead of evaluating offline video QA after the full video is available, it tests whether a model can process a video stream as it unfolds, remember past events, perceive the current moment, and proactively respond when future clues appear. Its retrospective memory, live perception, and proactive response tasks make it a strong evaluation reference for this project.

ReMEmbR. NVIDIA ReMEmbR is a long-horizon embodied robot memory system. It uses a VLM to caption video clips, stores captions, embeddings, timestamps, robot poses, and visual evidence in a vector database, then lets an LLM agent retrieve and reason over spatial, temporal, and navigation questions. It is a strong caption-level RAG memory baseline.

StreamBridge. Apple StreamBridge aims to convert offline Video-LLMs into proactive streaming assistants. It uses a memory buffer, round-decayed compression, and an activation model to support long video streams, multi-turn interaction, and proactive response timing. It is directly relevant to streaming Video-LLMs, but its memory is closer to context compression than persistent, queryable infinite external memory.

Main limitation. Most prior work still uses explicit memory representations: text queries, captions, summaries, vectorized captions, or written memory bodies. This makes the memory easy to inspect, but it also throws away visual detail, timing, and weak signals. In a streaming-video setting, that compression can cause the system to forget exactly the small events it may need later.

Key contribution: continuous memory fields

Show full description

A core design choice is what the continuous field actually is. The explicit memory buffer is the real long-term memory: it stores the evidence and models the actual distribution of what the stream contained. The continuous field is not that store — it is a learned, bounded-size retrieval prior over the buffer. Given a query it models where the relevant memory likely lives, so the agent can sample from the buffer instead of scanning all of it, then move step by step: find anchors, follow temporal or semantic gradients, inspect evidence, refine the path.

Buffer is the memory; the field is the prior. The buffer stores evidence in tiers — raw clips for hot, schema and pointers for warm, compact summaries for cold — and it is queried by sampling. The field never stores or reconstructs evidence; it only predicts where to sample. Querying long-term memory therefore means importance-sampling from the buffer under the field's guidance, and the answer is always grounded in concrete evidence pulled from the buffer.

Why a continuous prior at all? Streaming video is an unbounded intake. We keep storage bounded by tiering and compressing the buffer, and we keep search tractable by learning a fixed-size continuous prior over it rather than scanning a flat vector store. Video memory is uncertain, dense, and continuous — events overlap, object states change gradually, useful evidence lives between obvious clips — so a continuous, query-conditioned prior (flow matching or diffusion) is a natural way to model where to look and to transport a query toward the right region of the buffer.

Tiers and graceful degradation. All tiers live in the buffer at different fidelity. Hot memory keeps raw clips and dense features for exact grounding; warm memory keeps schema and pointers that are partly re-inspectable; cold memory keeps compact summaries. The field guides which tier and region to sample, not what the answer is. Recent answers stay exact; older answers degrade to gist with a confidence, so the target is graceful forgetting rather than catastrophic hallucination.

  • Buffer = memory: the explicit tiered buffer stores evidence and models the actual long-term distribution.
  • Field = prior: a learned, bounded-size retrieval prior over the buffer; it never stores or reconstructs evidence.
  • Query = sampling: querying long-term memory means importance-sampling from the buffer under the field's guidance.
  • Why continuous: a fixed-size continuous prior keeps search tractable over an unbounded, tiered buffer.
  • Grounding rule: answers are always grounded in concrete evidence pulled from the buffer.

Core contribution and ICLR positioning

Show full description

Thesis. Streaming video memory should not be framed as a larger context window or a growing caption store. It should be framed as distribution-guided evidence navigation: keep a grounded evidence buffer as the memory, learn a query-conditioned retrieval distribution over that buffer, and let an interactive two-agent system construct, navigate, and answer from the memory in real time. The core, ICLR-level claim (upgraded in 021) sharpens this into a falsifiable statement: under a fixed bit budget with unbounded intake, discrete retrieval is information-theoretically capped once events exceed storable tokens, whereas an amortized continuous memory field degrades gracefully — so the field is necessary, not merely convenient, past a measurable discrete ↔ amortized crossover.

Task formulation. The ICLR-level problem should be explicit: Streaming Multi-hop Memory QA. A video stream arrives online as S_t = {x_1, ..., x_t}; the model cannot assume the full video is available in advance; a user query q can arrive at any time; the answer must be supported by a cross-time evidence chain E* = (m_a, m_b, m_c, ...) with timestamps or clip pointers. Evaluation should stress horizon growth, bounded memory, latency, and whether the answer is grounded.

Method claim. The explicit buffer B_t = {m_i} stores real evidence units: clip pointer, timestamp, entities, schema, latent keys, tier, and importance. The learned component is not the memory itself; it is a navigation prior p_theta(m | q, h, B_t), where h is the current retrieval session: anchors found, visited regions, partial evidence chain, and uncertainty. Multi-hop retrieval becomes repeated sampling / navigation under this distribution, followed by snapping back to real buffer evidence.

System claim. The front-end agent remains close to the user: live context, interaction, and in-context query decomposition. The back-end agent owns memory construction and multi-hop navigation: ingest evidence, maintain the buffer / graph / field, run stateful retrieval sessions, and return typed, timestamped evidence to the front-end. The front-end should not answer from the field; it answers from retrieved evidence.

What is new. Compared with caption-RAG or ReMEmbR-style memory, the method does not reduce long video to text captions alone. Compared with MovieChat / Flash-VStream-style memory compression, it is not only context management; it is persistent, queryable, evidence-grounded long-term memory. Compared with M3-Agent-style entity memory, the key addition is a learned continuous navigation distribution over the grounded buffer / graph. Compared with offline long-video QA, the setting is online, unbounded, and interactive.

Minimum viable contribution. If the continuous prior fails to beat a strong ANN / graph traversal baseline, the fallback paper should still stand on the task and system: a streaming multi-hop memory benchmark, a grounded two-agent memory architecture, and careful evidence-chain / forgetting-curve evaluation. The high-risk, high-reward claim is that distribution-guided navigation scales better as horizon grows under a fixed memory budget.

Difficulty 1: structure and hierarchy in memory

Show full description

Open question: how should the system model structure and hierarchy in video memory storage and query? A flat memory field is too vague for temporal relations, multi-hop reasoning, and evidence grounding. But a fully hand-crafted hierarchy like episode → event → clip → frame may be too rigid for open-ended streaming video.

The current working idea is to use a temporal-semantic graph as a scaffold, while letting useful structure emerge from the stream and from queries. State changes, prediction error, entity continuity, temporal proximity, repeated co-retrieval, and future query usefulness can all create or strengthen nodes and edges. The memory field then gives a coarse navigation signal over this graph; it tells the agent where to look, not what the final answer is.

After navigation, the trace should become a cue/reminder: “these anchors, entities, time ranges, and relations are worth checking.” The agent can then retrieve actual evidence into context and optionally update memory: create a new event node, link two clips, strengthen an entity relation, compress a redundant segment, or archive a low-utility trace. This discussion is still open; the main design question is how much structure should be learned versus specified.

A reasonable decomposition is: the graph stores interpretable structure, while diffusion / flow matching manages the uncertain dynamics on top of that structure. Nodes can represent frames, clips, events, entities, places, user goals, or summary memories. Edges can represent temporal order, same entity, state transition, causal guess, co-retrieval, or “often useful for the same query.” Flow modules can then operate on different parts: node activation flow, edge update flow, retention-state flow, and hierarchy-proposal flow.

The key is not to make every graph operation generative. Some operations should stay deterministic and auditable, such as storing raw evidence pointers. The learned flow is more useful for soft decisions: which nodes should wake up, which edge should be strengthened, which memory should be compressed, and which region of the graph should be explored next.

  • Graph role: keep memory structure inspectable through nodes, edges, and evidence pointers.
  • Flow role: manage uncertain activation, navigation, retention, and compression decisions.
  • Open question: decide which hierarchy should be specified and which should emerge from stream/query use.

Difficulty 2: efficient storage and retrieval

Show full description

The next open problem is efficiency: how do we keep the system useful in real time without trying to push the whole video stream into one context window? A possible split is to keep a front-end agent close to the user and a back-end memory agent close to the long-term store.

The front-end agent handles the live interaction. It keeps a small context window for three things: recent video intake, memory retrieved from the long-term buffer, and the current user goal. Its job is not to remember everything forever, but to understand the current moment and ask the back-end for the right evidence when needed.

The back-end agent maintains the long-term memory distribution. As new video comes in, it converts raw intake into manageable evidence units and schemas: clips, event candidates, entity tracks, relations, summaries, and raw evidence pointers. A diffusion or flow-matching module can then update the current memory distribution so it reflects the stream so far: which memories are active, which are likely useful, which should be compressed, and which should stay retrievable but cold.

Because video is extremely information-dense, the schema and video clips should be treated as concise query and storage handles, not as the whole memory. A schema may say “person A picked up the phone near the desk,” and a clip pointer may keep the actual visual evidence. The compact schema makes retrieval cheap; the linked clip keeps the answer grounded when visual details, timing, or object state matter.

Flow matching vs diffusion. Diffusion is more mature and natural as a generator or denoiser. Flow matching feels more natural for this memory setting because it resembles latent transport: moving a query or memory state toward the useful region quickly. So the claim should not be “flow is better,” but: flow matching may be better suited for real-time memory navigation and buffer management, while diffusion may be better for reconstruction, denoising, or sampling missing context.

  • Front-end context: recent video, retrieved evidence, and current user goal.
  • Storage handle: schema and clip pointers make dense video queryable without replacing raw evidence.
  • Model choice: flow matching is a navigator/updater; diffusion is more natural as denoiser/reconstructor.

Multi-hop QA as evidence-chain retrieval

Show full description

Multi-hop QA makes this memory design more necessary. Long-video questions are often not answered by finding one relevant clip; they require evidence across multiple time points, entity states, and event relations.

Example: “After I picked up the phone from the desk, before I put it into my pocket, who did I talk to?” This requires several hops: find the initial state where the phone is on the desk; find the pick-up event; track the phone and the user along the timeline; find the pocket event; retrieve social interactions inside that interval; then aggregate evidence into an answer.

So retrieval cannot be only top-k similarity search. A better framing is query-guided memory traversal: query → anchor events → temporal/entity graph expansion → intermediate evidence retrieval → path verification → context window. Graph and schema matter because multi-hop reasoning needs explicit relations: before / after, same entity, state transition, inside time interval, causal or likely-caused-by, co-occurred with, user-goal related, and object ownership or possession.

Flow matching or the memory field can provide soft navigation. It does not directly answer the question; it predicts where the next hop should go. One concise design statement is: memory field handles where to search; graph handles how evidence is connected; raw evidence handles whether the answer is true.

For multi-hop QA, the front-end agent’s context window should behave like a small reasoning workspace, not a one-shot top-k dump. It should hold the current query, found anchor events, candidate path, evidence snippets for each hop, missing evidence or uncertainty, and the next retrieval action. The back-end should return an evidence chain, such as anchor A → relation → anchor B → relation → clip C → answer support.

This also explains why video density matters. If early compression keeps only captions, many middle hops disappear. Multi-hop QA needs raw pointers and dense features so the second or third hop can still be grounded in actual video evidence.

  • Retrieval pattern: query-guided traversal instead of one-shot top-k search.
  • Reasoning workspace: keep anchors, candidate path, evidence snippets, and next action in context.
  • Evaluation driver: require verifiable evidence chains, not just plausible answers.

Methodology: two-agent memory loop

Show full description

The methodology can follow the spirit of the interaction-model framework: keep one front-end agent close to the live user interaction, and one back-end agent close to the long-term memory system. The front-end agent is responsible for presence, context, and query decomposition. The back-end agent is responsible for memory maintenance, distribution updates, and evidence retrieval.

The front-end agent receives two kinds of visual context: recent real-time video intake, and evidence retrieved from long-term memory. It keeps a bounded context window containing the current user goal, recent stream observations, retrieved clips or schemas, and the current reasoning state. When new video arrives, the front-end converts it into concise query handles: clip pointers, event candidates, entity tracks, object states, temporal anchors, and raw-evidence references. These schemas are for storage and querying; they should not replace the dense video evidence.

When the user asks a high-level goal or a multi-hop question, the front-end agent turns it into executable hops. For example, “After I picked up the phone just now, and before I put it in my pocket, who did I talk to in between?” becomes: find the phone entity, find the pick-up event, find the pocket event, define the time interval, search for conversation events inside the interval, then ask for supporting clips. The front-end sends these hops to the back-end agent as structured queries rather than one vague text query.

The back-end agent maintains the long-term store and a changing memory distribution. As schemas and video evidence arrive, diffusion or flow matching updates distributions over event scope, entity scope, temporal range, and memory importance. The point is not to generate the answer directly. The distribution acts as a coarse cue: which part of memory should be activated, which evidence range should be sampled, which old memory should be compressed, and which clip should enter the front-end context window.

Dialogue example. User: “After I picked up the phone from the table just now, and before I put it in my pocket, who did I talk to in between?” Front-end agent: “First I will break this into a few retrieval steps: find the phone entity, find the pick-up event, find the put-in-pocket event, define the in-between time interval, then retrieve conversation events inside that interval.” Back-end agent: “I will activate the corresponding event and entity distributions from those hops, and return candidate time intervals, the people involved, and inspectable video clips.” Front-end agent: “I put the returned evidence into the context window and answer from the concrete clips, instead of relying only on the memory field's guess.”

This methodology needs a real-time memory evaluation signal. The system should score whether the back-end distribution and importance sampler send the right evidence into the front-end context window under latency and budget constraints. The evaluation target is therefore not only answer accuracy, but also cue quality, evidence-chain completeness, retrieval latency, and whether important dense video details survive the schema compression.

  • Front-end agent: turns live video and high-level goals into executable query hops.
  • Back-end agent: updates memory distributions and returns concrete evidence scopes.
  • Importance sampling: decide which clips and schemas deserve space in the front-end context window.
  • Evaluation: score cue quality, evidence completeness, latency, and detail preservation.

Training and test-time learning

Show full description

The training plan should separate what can actually be updated. If the system uses API-based large models, such as Qwen models above 72B parameters, we should assume the model weights are fixed. Test-time adaptation then happens through memory, prompts, tool-use traces, retrieval policies, schema design, and agent instructions rather than direct model fine-tuning.

If we use smaller controllable back-end models, such as 7B-scale models, we may optionally update the back-end model when needed. This should be treated as a separate engineering choice: useful for cheaper local adaptation, but riskier for stability. The default design should still keep the front-end API model stable and put most learning pressure on memory management and the memory-distribution model.

What on-policy distillation means. Ordinary distillation trains a student on a fixed offline dataset: sample an input from D_offline, ask the teacher, and imitate the teacher output. On-policy distillation instead trains on the states induced by the student’s current policy. The student first runs in the real task, producing its own queries, memory trajectories, retrieval paths, memory updates, and mistakes. A teacher, verifier, or reward model then corrects those states, and the student learns from the states it actually visits.

In the memory-agent setting, the student is not the whole memory. It is the memory controller: pi_theta(a_t | h_t, M_t, q_t), where h_t is interaction history, M_t is the current memory buffer or memory distribution, q_t is the current query, and a_t is a memory operation such as retrieve, update, forget, compress, merge, split, navigate, verify, or stop. The teacher provides a better action distribution or corrected action sequence for the exact memory states the student created.

This matters because long-term memory failures are distribution-dependent. The dangerous cases are not only clean benchmark queries, but agent-induced failures: vague queries, stale memories, conflicting memories, over-compressed events, memories that should have been forgotten, details that were forgotten too early, and multi-hop retrieval paths that get stuck in the wrong region. On-policy memory distillation trains directly on these self-induced failure modes.

The clean architectural separation is: memory storage / representation is the explicit hierarchical buffer; memory dynamics / distribution modeling is the query-conditioned latent memory field learned by flow matching or diffusion; memory control is the policy that decides how to use memory. OPD trains the memory controller. It is not the memory architecture, and it does not by itself create infinite memory.

A practical pipeline is: the student memory controller runs during interaction; the system logs a trajectory such as query → memory navigation → retrieved memories → answer; a teacher or verifier checks support, freshness, efficiency, and correctness; the teacher proposes corrected operations; then the controller is distilled with behavior cloning, KL to teacher actions, or preference learning over better and worse trajectories. The reward can combine answer accuracy, evidence support, efficiency, freshness, and penalties for stale or unsupported memory.

Flow matching / diffusion and OPD are therefore not competing ideas. The flow or diffusion model learns a query-conditioned memory belief or transition field in latent memory space. The controller learns how to use that field: whether to follow the flow, jump to a higher hierarchy node, expand a memory region, reject stale evidence, update a node, compress a segment, or stop retrieval. On-policy trajectories can also provide auxiliary supervision for improving the cue field, but the safest claim is that OPD is the training mechanism for the memory controller.

Trainable spec: turning the memory field into a model

Show full description

The continuous field stays a metaphor until it is written as a trainable model. This section pins down the latent space, the query conditioning, the supervision, and the cold-start, and it makes one positioning explicit: the field is a learned retrieval prior over an explicit memory buffer, not the store itself.

Buffer tokens and the field over them. The buffer stores per-clip tokens m_i = (z_i^sem, z_i^app, tau_i, entity_i, ptr_i): z_i^sem is a VLM-encoder embedding aligned with text queries; z_i^app is an optional video-diffusion (VAE) latent for dense appearance and dynamics; tau_i is the timestamp; entity_i is an entity id; ptr_i points back to the raw clip. These tokens are the actual long-term memory. The continuous field is a learned, query-conditioned prior over this buffer — it models where relevant tokens are likely to be, so retrieval becomes sampling from the buffer rather than scanning it. The discrete tokens are the evidence; the field is only the density used to navigate them. Storage is per-clip, indexed by time and entity, with the temporal-semantic graph from Difficulty 1 on top.

VLM encoder vs diffusion encoder. A VLM encoder gives semantic, language-aligned latents that make query conditioning and grounding easy and cheap; it is the natural retrieval key. A diffusion (VAE / denoiser) encoder gives a generative latent where “sampling memory” is literal and dense visual detail survives, which matters for hard multi-hop hops. The recommended design is dual-channel: VLM latents for semantics and query alignment, diffusion latents as the substrate the field actually models and samples. The minimal viable version uses only the VLM latent plus contrastive alignment and a conditioned flow; the diffusion reconstruction head is added later.

Query conditioning and flow I/O. The query text is encoded by the same VLM text encoder into q in the shared space. The flow velocity network v_theta(z_t, t | q, h) is conditioned on q, the reasoning history h (current anchors, found evidence), and a coarse time prior via cross-attention or FiLM. Input is the flow-time noisy latent z_t plus conditioning; output is the velocity (flow matching) or score (diffusion). Sampling integrates a base sample to z_1, which is snapped to the nearest real token to fetch a clip. For multi-hop, each hop re-conditions the field on updated h, so traversal becomes a conditional distribution moving step by step.

Supervision (the crux). Supervision stacks three layers. (1) Unconditional density: a standard flow-matching / diffusion objective on all memory latents learns p(z) directly from the stream with no labels, which also bootstraps cold-start. (2) Conditioned targets toward supporting-evidence latents, with pairs from self-supervised pretext (mask a future segment, use its caption / event as a pseudo-query), from a strong VLM that auto-generates multi-hop QA and evidence chains over the crafted stream dataset, and from on-policy retrieval hits where verified-correct answers turn their supporting clips into positives (this ties back to the on-policy controller training). (3) Contrastive alignment keeps query and supporting-clip latents close. A compact loss: L = L_density + L_cond + L_align + lambda * L_recon (optional diffusion reconstruction for dense detail).

Cold-start. Cold-start is handled by offline pretraining the field on the crafted stream-video dataset, so the velocity network already knows what video-memory latents look like. At deployment a fresh stream starts with an empty buffer; while the buffer is small the system degrades to direct retrieval over the few tokens and leans on the front-end context window, and entity / time priors from the recent window warm-start the conditioning. As the stream grows, the field takes over.

Why not neural-field as storage. A pure neural-field memory — fitting the memory distribution into a network's weights — is tempting for the bounded-storage thesis, but it is the wrong primary store for a grounding-heavy, multi-hop, real-time setting: weights return reconstructed latents, not verifiable clip pointers; online continual fitting risks catastrophic forgetting; and deletion / unlearning is hard. So the buffer stays the memory and the only source of grounded evidence, and a network that fits the distribution is deployed as a sampler / router over the buffer (where to look) — at most an optional compact cold-tier gist with confidence, never the system we ground answers on. The open research problem is controlled sampling and forgetting: which region to sample, what to compress, and how importance is set.

Crafting the dataset. Concatenate long egocentric and web streams into hour-scale continuous streams keeping raw frames, audio, and timestamps; encode clips with the VLM encoder into semantic latents and an auto schema, plus optional diffusion latents; auto-generate multi-hop QA, evidence chains, and temporal-grounding labels with a strong VLM and human-verify a subset; add pretext tasks; store query / evidence / answer / timestamp tuples as conditioned targets and all clip latents as unconditional density targets.

Buffer construction: distribution-faithful + importance sampling

Show full description

Since the buffer is the memory and the only grounded-evidence source, how it is built, compressed, and pruned is now the core of the method. Two principles drive it: (1) the buffer should reflect the actual distribution of the stream, and (2) actually essential events must be remembered, via importance sampling.

Principle 1: reflect the actual distribution. The buffer should be a faithful, compressed sample of the stream, so its density matches what really happened — not an arbitrary recency window. Redundant, high-density regions (the agent sitting at a desk for an hour) get compressed and merged; rare regions keep coverage. Concretely, the field's learned p(z) should match the stream's true distribution, which only holds if the buffer it is trained on is itself distribution-faithful. This is the streaming-sample view: like reservoir sampling, keep a bounded sample whose statistics track the full stream.

Principle 2: remember essential events (importance sampling). Pure frequency or recency would drop rare-but-essential events (a one-second handover, a key promise, a safety incident). So retention is importance-weighted: essential events are over-retained at high fidelity even when infrequent, and we store their importance weight so the field and retrieval can debias. This is literally importance sampling — sample from a proposal that over-weights essential events, and carry the weights to stay unbiased.

Reconciling the tension. Reflecting the distribution (sample by frequency) and remembering rare essentials (over-sample by importance) pull in opposite directions. The resolution is stratified, importance-weighted retention: keep a distribution-faithful base sample, plus an over-retained set of high-importance events, with weights recorded so query-time sampling stays a correct importance-sampling estimate rather than a biased one.

Where importance comes from. The importance signal is a mixture: novelty / surprise read from the field (low density under the current p(z) means new, worth keeping), recency, actual usage frequency (clips that were retrieved and supported correct answers), a learned future-utility predictor (will this be needed by later queries?), and explicit user or task signals. Start with a heuristic mixture, then learn the weights.

Tiers, summaries, dedup. A clip enters hot; time, capacity, and importance trigger demotion. Hot keeps raw clips and dense features (exact grounding); warm keeps schema (entities, relations, timestamps) plus a low-dim latent and a pointer; cold keeps a short gist plus a few keyframe latents and a confidence, raw dropped. Cold can therefore only ground coarse, gist-level answers — if a query needs cold-tier detail, the system should abstain or flag low confidence. Near-duplicate clips merge in latent space into an event node (representative + count + time span); entity tracks merge by appearance, co-occurrence, and name.

Training the policy safely. Importance is best learned as deferred-utility prediction: log which clips were later retrieved and supported correct answers, and train importance to predict future need — supervised, not sparse RL. During training, destructive demotion / compression is made reversible via a shadow store, so we can compute the counterfactual "would this query have succeeded if we had not compressed this?" and get dense supervision without permanently destroying evidence. On-policy distillation then refines only the failure modes heuristics miss. A falsifiable bar: at a fixed storage budget, the learned policy must beat FIFO, LRU, frequency, and uniform compression on the forgetting curve and multi-hop accuracy.

  • Remember essentials: importance sampling over-retains rare-but-essential events and stores their weights to debias.
  • Reconcile: distribution-faithful base sample + over-retained high-importance set, with weights kept for correct sampling.
  • Importance signal: field surprise + recency + usage frequency + learned future-utility + user/task.
  • Tiers + dedup: hot raw → warm schema → cold gist; merge near-duplicates; cold grounds only gist, else abstain.
  • Train safely: deferred-utility supervision + shadow-store counterfactuals; must beat LRU / frequency at a fixed budget.

Difficulty 3: the two-head seam (short-term context ↔ long-term buffer)

Show full description

The design has two memory heads: a short head — the front-end context window holding live video, the current goal, and working reasoning state — and a long head — the back-end buffer holding consolidated long-term memory. Most real queries need both at once, fusing “what is happening now” with “what happened earlier.” Whether the current buffer and agent actually support this two-head query is still open; this section records the seams where they do not.

Seam 1: the recent boundary. In interactive use the most-queried memory is the last seconds to minutes, but that is the least-processed region of the buffer: not yet schema-extracted, deduped, indexed, or importance-scored. The buffer is tuned for aged memory, so it is weakest exactly where the two heads meet. There is no defined warm-recent handoff between the context window and the consolidated buffer.

Seam 2: the fusion contract. The short head is not a buffer at all; it is LLM attention over tokens. A two-head query therefore means querying context (implicit, in-model) and the buffer (ANN / field) and then fusing them — but the fusion is unspecified: how retrieved evidence re-enters context, how it is deduped against what is already there, and how to keep the long head from contradicting the short head. A well-built buffer does not solve this, because fusion lives in the seam.

Seam 3: stateful retrieval. Two-head multi-hop is iterative: each hop carries forward found anchors. But a one-shot retrieve(query, k) is stateless, so every hop re-pays full retrieval latency and loses context. Multi-hop needs a retrieval session on the back-end (carried anchors, visited regions, partial evidence chain). The reasoning workspace in idea 009 lives on the front-end, so today neither side cleanly owns iteration.

Agent-side risks. Two more. First, the trainable part is downstream of the hard part: query decomposition — turning a vague two-head question into executable hops and deciding when to hit long-term memory — sits in the frozen API front-end, while on-policy distillation only trains the controller. Second, the back-end lumps three workloads with opposite profiles: ingest (always-on), maintenance (heavy, batchable), and serve (latency-critical). On an always-on stream these contend, and field retraining can stall a query.

Working directions (none settled). (1) Add a shared staging / warm-recent tier between context and buffer as the explicit seam. (2) Define a fusion contract where long-head evidence enters the short head as typed, deduped, timestamped, provenance-tagged tokens. (3) Make retrieval stateful via a RetrievalSession. (4) Move query decomposition into the trainable lane: the controller proposes hops, the frozen model judges and answers. (5) Split the back-end into three decoupled lanes — ingest, maintenance, serve.

  • Two heads: short = front-end context window; long = back-end buffer; real queries need both.

  • Fusion unspecified: how retrieved evidence re-enters context and is deduped is undefined.
  • Stateful multi-hop: retrieval is one-shot; it needs a carried-anchor session.
  • Agent risk: the trainable controller is downstream of frozen query decomposition; ingest / maintain / serve contend.

Working direction: query-quality critic over a frozen proposer

Show full description

This is a candidate fix for the agent-side risk in Difficulty 3 (the trainable part sitting downstream of query decomposition), but it is itself still open. Query decomposition seems to belong in the trainable lane, yet a generative decomposer is hard to train: there is no single correct hop decomposition — many sequences are valid — so teacher-signed gold decompositions are brittle. They reflect the teacher's style, overfit to one reference, and do not know what the buffer actually holds. So decomposition may not be cleanly supervisable.

Reframe: train a critic, not the actor. Keep the frozen API model as the proposer of candidate decompositions / next hops, and train a lightweight query-quality critic that ranks the candidates and decides whether to accept or re-propose. The actor needs no training; the critic needs only ranking / reward signals, not gold decompositions. This also promotes the “cue quality” idea from ideas 008 and 010 from an evaluation metric into a trainable objective.

What query quality is. A hop is high-quality if it is groundable (the buffer returns evidence with small snap distance and high confidence, not empty or vague), advances the chain (reduces answer uncertainty / yields information gain), is necessary (not already answerable from the short head — this directly serves two-head), and non-redundant with prior hops. Roughly quality(h) = w1·groundability + w2·advance + w3·necessity − w4·redundancy.

Signals without gold (teacher as judge, not labeler). Retrieval feedback — immediate and self-supervised (top-k margin, snap distance, whether groundable evidence returned), good for cold-start. Answer outcome — deferred and weak (a verified-correct chain gives positive credit to its hops, a wrong one negative). LLM-as-judge — the strong model judges whether a hop was useful given the retrieved evidence (judging, not generating gold). Counterfactual via the shadow store — would the answer have succeeded without this hop? Train the critic by ranking loss or regression to credit — a critic-only setup, far more tractable than a generative decomposer.

Why it stays open. Two risks keep this a question rather than a method. (1) Query quality must be separated from buffer recall: a hop can be right while the buffer fails to retrieve it; if only retrieval feedback is used, good hops get punished for buffer failures, so credit assignment must distinguish “asked wrong” from “asked right but not found,” which needs answer outcome and counterfactuals to anchor. (2) Reward hacking: rewarding groundability alone favors easy-but-useless hops, so the answer-level outcome must anchor the signal.

  • Don't train a generative decomposer: it needs gold and overfits style; freeze the proposer, train a critic.
  • Query quality: groundability + advance + necessity − redundancy.
  • Signals without gold: retrieval feedback + answer outcome + LLM-as-judge + counterfactual.
  • Reuses cue quality: promotes the 008/010 cue-quality metric into a trainable objective.
  • Open risks: separate query quality from buffer recall; anchor on answer-level outcome to avoid reward hacking.

Unified memory architecture: buffer, graph, field, and session

Show full description

This section fixes a coherence risk in the current design: buffer, graph, and field are not three competing memory systems. They are layers in one architecture. The buffer stores evidence. The graph organizes evidence. The field guides navigation over the buffer / graph. The retrieval session controls multi-hop state. The front-end context answers only from returned evidence.

Layer 1 — evidence buffer (storage). The buffer is the memory body and the only grounding source. Each entry keeps a clip pointer, timestamp, modality features, entity / schema fields, latent keys, tier, importance, and confidence. Hot / warm / cold only change fidelity; they do not change the rule that answers must snap back to real buffer evidence.

Layer 2 — temporal-semantic graph (structure). The graph is an index over buffer entries, not a separate memory store. Nodes can be clips, events, entities, places, goals, or summaries; edges encode temporal order, same entity, state transition, co-occurrence, likely causality, co-retrieval, or repeated usefulness for similar queries. The graph makes multi-hop traversal inspectable and gives the back-end explicit relations to follow.

Layer 3 — query-conditioned field (navigation). The field is a learned navigation prior over buffer tokens and graph nodes. Formally it can score or sample p_theta(m | q, h, B_t, G_t), where h is the current retrieval session. It does not store evidence, write answers, or replace graph structure. Its job is to decide which region, node, edge, tier, or next hop should be activated.

Layer 4 — retrieval session (control). A session holds anchors found so far, visited nodes, rejected candidates, uncertainty, and partial evidence chains. This is where multi-hop becomes stateful rather than repeated one-shot retrieval. The back-end agent owns this layer: it uses the field to propose directions, the graph to expand relations, and the buffer to snap every candidate back to concrete evidence.

Layer 5 — front-end context (reasoning / answer). The front-end receives typed evidence packets: clips, timestamps, schemas, confidence, provenance, and missing-evidence flags. It may decompose the next query step in-context, but it should answer only from retrieved evidence, not from the field's latent belief. This keeps the system auditable.

  • Buffer: storage layer; stores grounded evidence and tiers.
  • Graph: structure layer; organizes buffer evidence into traversable relations.
  • Field: navigation layer; scores / samples where to look next over buffer + graph.
  • Session: control layer; keeps anchors, visited regions, uncertainty, and evidence chains.
  • Frontend: answer layer; reasons over returned evidence, not over latent field guesses.

Repositioning: the field is access and management, not storage

Show full description

This refines 005, 006, 013, and 017 and fixes the most attackable claim in the project: do not justify the continuous field as "we need it to store infinite memory." Storage is, and stays, discrete: the grounded evidence buffer, the index, the graph, gist tokens, product quantization (PQ), and coresets. The field only earns its place if it adds value on top of that discrete storage — never by claiming it solves "can't store it all."

Cleanest positioning. Don't say "we need a continuous field to hold infinite memory." Say: "we need a grounded evidence buffer to store verifiable memory; on top of it we explore a query-conditioned continuous field that models which memories are likely relevant, which regions are worth retrieving, and which memories to retain or compress." The division of labor: the buffer answers where the evidence is and whether it is traceable; the graph answers how evidence connects; the field answers where to look, what to keep, what to degrade. The field is a navigation and management layer, not a warehouse.

Justification A — field as retrieval prior (stateful navigation). Long-video multi-hop QA is usually not a one-shot top-k problem: find anchor → walk temporal / entity / event relations → verify intermediate evidence → update query → retrieve again. The field predicts, given the query, found anchors, visited regions, and uncertainty, which memory region / graph node / tier to visit next: p_theta(m | q, h, B_t, G_t). Its value is not "store more" but "make retrieval stateful navigation rather than one ANN top-k." Risk to be honest about: this function does not require a generative field — a discriminative learned next-hop policy (a conditioned GNN / reranker over the graph) is simpler and likely stronger. So A must beat not only ANN-only, ANN + graph, graph-only, and M3-Agent-style memory, but specifically a learned discrete next-hop policy. That ablation is what isolates the field's generative form from its function. A is the role most at risk of being dominated by a discriminative policy.

Justification B — field as retention / compression prior (the strongest fit). Retention is genuinely a density / novelty problem, which is exactly what a generative model of p(z) is good at: low density under the current field = novel = worth keeping. So the field can decide what enters the hot layer, what events merge, what is compressed to a gist token, what degrades to cold, what low-value clips are dropped, and what rare-but-future-useful events must be kept. It models memory density / novelty / retention importance and manages the storage budget instead of becoming storage. Important split: "future utility" should be a supervised deferred-utility predictor (see 014), which is discriminative; the field's unique contribution here is only the density / novelty signal. This is a far stronger claim than "the field stores infinite memory."

Justification C — field as lossy semantic recall / reminder (downgraded). This is the only place close to "field as memory," and it must stay downgraded. When raw evidence has been compressed, dropped, or reduced to a cold gist, the field may generate a low-confidence semantic reminder ("there was probably a phone-related interaction here"). This is never a grounded answer — only a hypothesis / cue / reminder. The system must then check the buffer for a matching gist token, summary, event node, or time range; if no evidence is found, it answers with low confidence or abstains. So C is graceful degradation, not the main line. The irony to state openly: C is the only role that intrinsically needs generativity; A and B can both be done discriminatively. So the most "field-like" role is the one we deliberately keep non-core.

Reviewer-safe thesis. "We do not claim that a continuous field replaces external memory storage. Instead, long-horizon video memory needs two complementary components: a discrete evidence buffer for grounded storage, and a continuous query-conditioned field for modeling retrieval, retention, and degradation over that buffer. The buffer stores what can be verified; the field predicts where to search, what to preserve, and how to gracefully degrade under bounded memory."

Arguments to retire. Stop using: "ANN can't scale to long video," "the vector index overflows," "the continuous field is the infinite-memory body," "the field stores what the buffer can't," "context is limited so the field is necessary," and "long video is long, so a continuous field is naturally necessary." The safe chain is instead: context is limited → we need external memory → the external-memory body is a bounded evidence buffer → on that buffer the field is only a learned retrieval / retention / degradation prior whose necessity is empirical.

Recommendation (updated by 021). The field is the chosen high-risk, high-reward core contribution, and its "necessity is empirical" clause is made concrete as the discrete ↔ amortized bit-budget crossover (021). The discrete-first discipline in this section is not a demotion of the field but its honest guard rail: build the strong discrete baselines (ANN + graph + gist tokens) that share the same bit budget, because they are exactly what the crossover must beat. The stable fallback — Streaming Multi-hop Memory QA + a grounded buffer / graph / session architecture + evidence-chain evaluation — is what keeps the paper alive only if the crossover fails (the kill criterion in 021).

Empirical plan and attribution traps for the field

Show full description

Following the repositioning in 019, this fixes what must actually be proven and the credit-assignment traps that could make a "win" meaningless. What we should not try to prove: that the field beats FAISS at single nearest-neighbor lookup — that almost certainly fails. The field has to earn its place on horizon scaling, retention, or forgotten-memory recall, under a fixed memory budget.

Experiment 1 — fixed-budget horizon scaling. Grow the stream (10 min → 1 h → 4 h → 8 h → 24 h) with a fixed memory budget measured in bits, not token count, so amortized (weight) memory is compared fairly; this is the setup whose crossover is the hero result in 021. Baselines: ANN over retained embeddings; ANN + graph traversal; ANN + PQ / coreset / gist token; caption-RAG; M3-Agent-style memory; a learned discrete next-hop policy (non-generative); field-guided graph / buffer navigation; field-guided retention + navigation. Metrics: evidence-chain recall, multi-hop accuracy, retrieval steps, latency, old-memory forgetting curve, hallucination rate. A field win should show up as more stable multi-hop evidence-chain recovery as the horizon grows, not as single-hop top-k.

Experiment 2 — retention policy. Fixed memory budget, same incoming stream, vary only retention: FIFO, LRU, reservoir sampling, frequency-based, novelty-based, heuristic importance, learned importance predictor, field-guided retention. The storage-related justification (B) holds only if field-guided retention keeps more of the evidence that future queries actually need at the same capacity.

Experiment 3 — forgotten-memory gist recall (riskiest, most unique). Deliberately drop a fraction of raw clips, keeping only compressed cold memory. Compare ANN over gist tokens, PQ / coreset, summary buffer, graph summary, field-generated gist, and field + snap-to-nearest cold token. Metrics: gist correctness, calibration, hallucination rate, deletion compliance, abstention quality. This is the only place the field's generative nature could be uniquely useful (justification C) — but a strong ANN + gist / PQ baseline will be hard to beat, so treat a positive result as the high-reward, not the expected, outcome.

Attribution trap 1 — horizon scaling mostly measures retention, not navigation. Under a fixed budget the buffer holds a bounded set; as the horizon grows, more is dropped, so old-evidence recall falls. ANN and field then search the same retained set: if the evidence was kept, ANN (with graph) finds it; if it was dropped, neither does. So Experiment 1's curve is dominated by what was retained (Experiment 2 / B), not by the navigation field (A). Do not attribute horizon-scaling gains to navigation. Isolate cleanly: to test navigation, feed every method the same retained buffer (retention fixed) and vary only the navigation strategy; to test retention, fix navigation and vary retention; if the hero figure uses horizon scaling, label and attribute it as a retention / whole-system result, not a navigation-prior result.

Attribution trap 2 — form vs function. Without the learned discrete next-hop baseline in Experiment 1, a navigation "win" cannot be attributed to the continuous / generative form rather than to "any learned navigation." That baseline is mandatory.

Attribution trap 3 — query quality vs buffer recall. A hop can be correct while the buffer simply fails to retrieve it; with retrieval-only feedback, good hops get punished for buffer failures. Credit assignment must separate "asked wrong" from "asked right but not found," anchored on answer outcome and shadow-store counterfactuals (ties to 016).

Attribution trap 4 — density vs future-utility. In retention (B), keep the field's density / novelty signal separate from a supervised deferred-utility predictor; otherwise a retention win cannot be credited to the field rather than to the utility predictor.

  • Three experiments: horizon scaling, retention policy, forgotten-gist recall, all at fixed budget.
  • Trap 1: horizon scaling is dominated by retention; isolate navigation by fixing the retained buffer.
  • Trap 2: include a learned discrete next-hop baseline to isolate the generative form.
  • Traps 3–4: separate query quality from buffer recall, and density from future-utility.

Core thesis: the discrete ↔ amortized memory crossover (where the field becomes necessary)

Show full description

This is the core contribution. It upgrades the positioning in 006 and gives the "necessity is empirical" clause in 019 a concrete, falsifiable form, with the continuous flow / diffusion field as the center of the paper, not an optional module. The non-negotiable rule: for the field to be core and to clear an ICLR bar, it must claim what discrete retrieval fundamentally cannot do — not what it does slightly worse. If the pitch is "the field retrieves more accurately than ANN," a strong ANN + graph + learned-reranker baseline will dominate or tie, and the contribution collapses. The field must therefore stand on the capability boundary of discrete memory.

Four things discrete retrieval fundamentally cannot do. (1) Return what was never stored. ANN can only return stored tokens; after compression / forgetting the clip is gone, so ANN returns nothing or a wrong neighbor, whereas a model of p(z | q) can interpolate a latent hypothesis on the manifold (associative-memory / pattern completion). (2) Model density. Distribution-faithful retention and novelty / surprise (low density = novel = keep) require a density model; a discriminative importance predictor needs labels, while the field gives unsupervised density for free. (3) Bridge an incomplete graph. Discrete multi-hop needs the right edges to exist (cross-hour entity re-ID and causal edges are never fully built); continuous transport along the manifold can bridge missing edges, so the field's relative advantage grows as the graph gets sparser. (4) Give a posterior, not a point. The field yields a distribution over where evidence is, enabling calibrated abstention ("does this evidence even exist, and how sure am I?"); ANN returns distances, not a calibrated posterior.

The information-theoretic wedge. Frame memory under a fixed bit budget with unbounded intake. With budget B bits and per-token cost c bits, a discrete store holds at most B / c tokens. As the number of distinct events N grows without bound, eventually N > B / c: you cannot keep even one token per event, and discrete recall on the dropped events falls toward zero. An amortized model spends the same B bits on weights that approximate p(z); its per-event fidelity should degrade smoothly with N rather than collapsing to zero. The scientific claim is a crossover / phase transition: below some events-per-budget ratio discrete memory wins (this is exactly the regime 019 protects — do not claim "ANN can't scale" in general), but past the crossover, amortized distributional memory is necessary, not merely convenient. The contribution is locating and characterizing that crossover.

Hybrid, not a reversal. This partially re-admits the "neural-field as storage" idea that 013 rejected — but only for the long tail. The architecture stays hybrid: the discrete buffer exactly grounds recent / important evidence; the field's weights cover the long tail lossily and with calibrated confidence. Grounding is preserved because the field's output is a proposal, not an answer: the field generates a latent hypothesis → the system verifies it against whatever residual evidence exists (gist tokens, graph neighbors, time ranges) → if verifiable it answers grounded, otherwise it abstains with calibrated low confidence. The field expands recall; verification keeps answers traceable.

Core thesis statement. "We model unbounded video memory as a continuous, query-conditioned distribution learned by flow matching, giving a single mechanism for retention (density), retrieval (transport), and graceful degradation (sampling under uncertainty). Under a fixed bit budget, discrete retrieval is information-theoretically capped once events exceed storable tokens, whereas amortized distributional memory degrades gracefully — establishing a regime where a continuous memory field is necessary, not merely convenient."

Hero experiment (the crossover). Fix the budget in bits (fair to generative memory), grow the horizon until storable tokens per event drop below one, and plot evidence-chain recall / multi-hop accuracy against the events-per-bit-budget ratio. Baselines must spend the same bits: ANN + gist tokens, PQ / coreset, graph summary, and "more-but-coarser tokens." A field win is a visible crossover: past it, all discrete methods collapse while the field holds a meaningfully higher (lossy but non-zero) curve. Kill criterion (commit to it up front): if no crossover appears — i.e. discrete + gist tokens stay sufficient at every tested ratio — the field has no moat and the project falls back to the task + system + evaluation contribution.

Honest risk account. (1) The long tail may never be queried. If useful queries always land on recent / important evidence that the discrete buffer already holds, the field's long-tail coverage is academic. The benchmark must therefore deliberately include multi-hop questions that require hitting compressed / dropped evidence; without that, the crossover figure cannot be produced. (2) Hallucination. Generation-as-proposal + verification + abstention contains it, but calibrated confidence needs its own mechanism and its own experiment (currently unspecified). (3) Cost. This is the high-risk, high-reward path; a 10-week window likely yields only an early crossover signal on a dataset subset, not the full paper.
